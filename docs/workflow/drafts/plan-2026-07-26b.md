# Plan — 2026-07-26 (b)

Session input: four fixes on the removal receipt (`comprovante de remoção`) and the removal detail
modal. Board state: 1 open issue (#284, `status:proposed`, unrelated — QR label font size).

## Findings

1. **Receipt print size.** `app/globals.css:158-167` declares `@page { size: 100mm 50mm; margin: 0 }`
   inside `@media print`. `globals.css` is imported by the root layout, so this applies to **every**
   print surface in the app — the receipt is not "accidentally reusing" the tag page size, it has no
   way to opt out. Adding an A4 `@page` in a component won't fix it cleanly: both rules would be
   loaded and fight in the cascade. The label rule has to move to route-scoped CSS.
2. **Pedido box** (`components/removals/removal-print-view.tsx`) is a `<Card p-4>` with a bare
   `<span className="text-[13px] font-semibold">Pedido</span>`. Every other block on that page uses
   either the `dt` treatment (`text-xs text-muted-foreground`) or the
   `rounded-[14px] border border-border` + `bg-muted` header-strip treatment (items table). It is the
   only element following neither.
3. **Removals modal overflow.** `load-detail-modal.tsx:103` uses
   `max-h-64 overflow-y-auto rounded-[14px] border border-border`.
   `removal-detail-modal.tsx` has the same wrapper **without** `max-h-64 overflow-y-auto`, so a long
   item list grows the dialog past the viewport.
4. **Receipt button icon** — `removal-detail-modal.tsx` "Comprovante de Remoção" `Link` has no icon;
   sibling controls in `components/inventory/` all pair a lucide icon with their label.

5. **Removal modal item identity.** `lib/db/removal-items.ts:73` composes `identifier` as
   `Item {n} - {notaFiscal}`, where `n` is the item's number **within its originating load**. The
   modal ignores that field: it renders `Item {index + 1} — {item.notaFiscal}` (modal-list position)
   and then `{item.notaFiscal}` again in the next column. So the NF is duplicated *and* the item
   number is wrong whenever a removal spans more than one load. The load modal's middle column is the
   material; `getRemovalItems` already computes material and drops it at line ~86.

### Calls made

- **Paper size: A4 portrait**, confirmed in-session.
- **No feature flags** on any of the four. All are CSS/markup fixes (plus, in #289, keeping one
  already-computed field on a returned object) with no data or API surface; a kill-switch costs more
  than the single-commit revert it would replace. #286 has the real blast radius — it touches global
  print CSS — so it carries explicit QR-label regression criteria instead of a flag.
- All four are **user-visible: yes** → evidence gate. #286 and #288 screenshots must use
  `page.emulateMedia({ media: 'print' })`; a normal screenshot proves nothing for print-only CSS.
  #286 must show evidence for **both** routes, since breaking the labels is its main risk.
- **#289 was promoted from an observation to a ticket** during review of this draft: what looked like
  a cosmetic duplicate is a correctness bug (wrong item numbering across multi-load removals).

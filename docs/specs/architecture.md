# Architecture

Stack decisions with rationale. These are commitments unless a spec change goes through the board (see `docs/workflow/board-protocol.md`).

- **Frontend/Fullstack**: Next.js (App Router) — required.
- **API**: no separate backend. Server Actions for the main-flow mutations (add load, remove item); REST Route Handlers (`app/api/...`) only for endpoints that may need external consumption in the future.
- **Database**: Postgres via Supabase. Relational is mandatory — item removal is an ACID multi-table transaction that can span different loads; NoSQL was ruled out for this reason.
- **Auth**: Supabase Auth + Row Level Security in Postgres. Self-service signup is invite-code gated (see `docs/specs/business-rules.md#registration-auth`) — there is no public open registration. All auth code is retained even when a deployment runs as a public demo: a `DEMO_MODE` env flag (off by default) gates demo behavior — the server auto-establishes a session as a single seeded demo user, `/login` and `/register` redirect into the app, a persistent demo banner is shown, and the dataset resets nightly (see [ADR 0002](../adr/0002-demo-mode-flag.md), [ADR 0003](../adr/0003-nightly-demo-reset.md); behavior details in `docs/specs/business-rules.md#demo-mode`).
- **Viewer read-only, enforced at the database, not RLS**: the app connects to Postgres directly as its own role (`lib/db/index.ts`, `SUPABASE_DB_URL`), bypassing PostgREST/Supabase Auth entirely — so the RLS policies below (`authenticated_full_access`, `drizzle/0003_enable_rls_policies.sql`) are never evaluated against the app's own queries; they only guard the separate anon/PostgREST path. RLS policies therefore cannot enforce the viewer restriction against the app itself. The enforceable mechanism is a restricted Postgres role, `yms_viewer` (`drizzle/0017_viewer_role_enforcement.sql`, `SELECT` only, no `INSERT`/`UPDATE`/`DELETE`), which `withAuditUser` (`lib/db/audit-context.ts`) makes the app's connection assume via `SET LOCAL ROLE` for the duration of a viewer's transaction — transaction-local, cleared on commit/rollback, so it can never leak onto the next request on a pooled connection. This is a database-level backstop behind the application-level guard (`lib/actions/guard.ts`): even a mutation that forgets to call the guard still hits a Postgres permission error and rolls back.
- **Audit**: `audit_log` table populated by Postgres triggers (AFTER INSERT/UPDATE/DELETE) on the load, item, and removal tables.
- **ORM**: Drizzle (Prisma acceptable fallback if Drizzle blocks — decision to be settled by the first database task).
- **QR codes**: generation with the `qrcode` lib (one UUID per item); scanning via `html5-qrcode` or `@zxing/browser` directly in the browser (no native app). Printing via a dedicated route with CSS `@page { size: 100mm 50mm; margin: 0 }`, one tag per label, targeting the Elgin L42 Pro Full label printer.
- **Removal receipt**: printable/shareable comprovante de remoção, server-rendered at `/removals/<id>/receipt` (same dedicated-print-route pattern as the QR codes page — browser print dialog, no PDF generation library). The attached Pedido image lives in the private `removal-pedidos` Storage bucket, so the route resolves a short-lived signed URL server-side to render it rather than relying on a public bucket.
- **Print page sizes are route-scoped, not global**: `@page` is a document-level CSS at-rule — it can't be scoped with a Tailwind `print:` utility or a selector, and a shared global stylesheet can only ever declare one `@page` rule per property (a second one doesn't override the first per-route, it just conflicts in the cascade). Each print route therefore owns its own `@page` size, injected at runtime by the `PrintPageStyle` client component (`components/print/print-page-style.tsx`) rather than by a route-scoped CSS Module: `page.tsx` renders `<PrintPageStyle css={...} />` with a 100x50mm rule for QR labels (`app/(authenticated)/loads/[id]/print/page.tsx`) or an A4 rule for the removal receipt (`app/(authenticated)/removals/[id]/receipt/page.tsx`). `PrintPageStyle` inserts a real `<style>` element into `<head>` on mount and removes it on unmount. A CSS Module was tried first (issue #286) and does scope the stylesheet to the importing route on a hard navigation, but its `<link rel="stylesheet" precedence="...">` is a React 19 hoistable *resource* — React's unmount cleanup for that resource type only decrements a refcount, it never removes the node from `<head>`. Because every route sits under the same `app/(authenticated)/layout.tsx` shell and `PageBackHeader`'s back control is a `next/link`, leaving a print route is normally a soft (client-side) navigation, so the stale `@page` rule kept applying to whatever route the user visited next — including the other print route's, which then fought it in the cascade. A directly inserted `<style>` is a plain DOM node, not a resource, so its removal effect actually runs on unmount. `app/globals.css` keeps only the print rules that are genuinely app-wide (forcing a white background so screen chrome never bleeds into printed output) — it must never declare its own `@page` rule again (issue #286).
- **Validation**: Zod in Server Actions.
- **UI**: shadcn/ui + TanStack Table for the stock and removal tables.
- **Deploy**: Vercel (Hobby for dev/staging; Pro required in production due to commercial use — alternative: VPS with Coolify to cut cost).
